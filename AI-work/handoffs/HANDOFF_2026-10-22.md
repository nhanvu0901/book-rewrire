## 2. Project Purpose and Current Boundaries

`pov-retell` is a Python CLI project for extracting books and eventually supporting character-centered analysis and POV retelling.

| Stage | Current behavior |
| --- | --- |
| `pov extract` | Reads HTML/EPUB/TXT, uses an LLM to map book structure, and writes chapters and paragraphs to files. |
| `pov ingest <book_id>` | Reads that saved extraction, processes characters chapter by chapter, saves cumulative JSON, then writes selected `Character` properties to Neo4j. |
| Chapter summarization | Implemented as its own LangGraph workflow, currently disabled in ingestion. |
| Relationship verification and `RELATES_TO` edges | Not implemented in the current workflow. Saved relationships are proposals. |
| Event extraction, knowledge analysis, POV generation | Future work. |
| FastAPI backend / web UI | Not present in the current application flow. |

LangGraph coordinates sequential nodes and chapter loops. There is no checkpointing or resume. Its `recursion_limit` caps graph execution steps; it must allow all loop iterations and does not control model reasoning depth.

### Current character graph: identity LLM + ScaleDown attributes

```text
START -> initialize -> resolve_identities -> apply_identities
      -> extract_attributes -> update_characters -> save_json
      -> next chapter: resolve_identities, or END
```

1. **Resolve identities:** A general LLM receives the original chapter and a compact existing roster: IDs, names, aliases, and short identifying context. It returns characters active or referenced in that chapter, rather than the full accumulated roster.
2. **Apply identities:** Python assigns IDs to `new_N` proposals, updates names and aliases, and applies explicit merges. Characters absent from the current response remain in the roster.
3. **Extract attributes:** For each selected character, ScaleDown receives the entire current chapter and entity descriptions focused on that character. This is one extraction slot per active character, not one call per chapter.
4. **Update records:** Python validates and combines accepted profile data, resolves relationship target names where possible, and retains unresolved proposals separately.
5. **Save:** Writes raw proposals and the cumulative character state after every completed chapter.

Explicit merges keep the earliest surviving ID, flatten redirects, preserve complementary profile data, and redirect relationship targets. Same names alone do not imply a merge. Current chapter identity hints determine whether a same-name extraction is distinguishable; stale historical hints must not authorize it. Ambiguous cases can log `skip_ambiguous_attributes`.

### Saved character format

Illustrative record; IDs and names can differ between runs:

```json
{
  "character_id": "char_004",
  "candidate_name": "Lucy",
  "aliases": ["Lu"],
  "attributes": {
    "gender": "female",
    "species": "human",
    "age_description": null,
    "physical_description": null,
    "personality_traits": []
  },
  "relationships": {
    "char_001": "younger sister of Peter"
  },
  "resolution_status": "candidate"
}
```

`mentions` were removed at the user's request. A relationship map key is the target character ID; its description is from the source character's side. These entries are not verified Neo4j edges. Unknown or ambiguous targets remain pending instead of receiving guessed IDs.

### Summary graph: available but disabled

Inputs are the original current chapter, the previous cumulative book summary, book title, and chapter ID. Saved output contains `chapter_id`, `chapter_summary`, and `book_summary_so_far`.

- Chapter 1: one plain-text summary call; its result also initializes the cumulative summary.
- Later chapters: two plain-text calls, both using the original current chapter and previous cumulative summary: one for the chapter, one to update the cumulative summary.
- For 17 chapters, this is 33 summary calls before retries.
- Python assembles the JSON record and saves `summaries/uNN.summary.json` atomically.
- Validation checks nonblank output, not factual accuracy.

The old summary plan describes an earlier one-JSON-call design. The current implementation uses text calls because `scaledown/summarize` rejects `response_format`.

### OpenRouter adapters

`infrastructure/llm.py` separates three capabilities:

| Interface | Use |
| --- | --- |
| `JsonLLM.complete_json` | General LLM JSON output, Pydantic validation, semantic validation callback, and bounded repair retries. |
| `TextLLM.complete_text` | Plain-text summary output without JSON response format or sampling arguments. |
| `EntityLLM.complete_entities` | ScaleDown entity extraction with provider-specific entity descriptions. |

ScaleDown entities are sent under `extra_body.provider.options.scaledown.entities`. The JSON text in `choices[0].message.content` contains an envelope; the application validates its `structured_result`. Entity validation retries repeat the original source rather than replacing it with a conversational repair prompt.

Live schema probes showed that arrays of objects worked for aliases and traits, for example `[{"name": "..."}]` and `[{"trait": "..."}]`. Arrays of description strings produced empty objects, while JSON-schema-shaped objects inside `entities` were echoed as data. Python normalizes successful object arrays into the string lists stored in character JSON. These findings concern this OpenRouter route, not every ScaleDown API.

### Neo4j

The writer uses `(book_id, run_id, character_id)` as the unique character key. It stores `canonical_name`, `aliases`, `gender`, `species`, `age_description`, `physical_description`, `personality` as joined traits, and `resolution_status`.

It does not write mentions, `first_mention_id`, relationship maps, or `RELATES_TO` edges. It removes legacy `first_mention_id` and `relationships` properties on matched nodes. Current records remain `candidate`; completing ingestion does not verify their facts.

Neo4j writing starts only after all chapters finish. Failed chapter runs retain saved JSON but do not reach that final write.

## 5. Work Completed and Important Fixes

Earlier work moved the LLM provider to OpenRouter, moved book data under the repository's `book/` folder, added `.env` configuration and model settings by graph, organized graph-local files, added chapter summaries, and added fake-client unit tests plus opt-in real API tests.

Recent identity and ScaleDown work addressed these specific issues:

| Issue | Current treatment / limit |
| --- | --- |
| `names_in_chapter` had to match source text verbatim | Removed at the user's request; valid identity reasoning must not fail solely on wording. |
| Canonical name had to belong to old/returned names | Removed; this could reject a valid `Faun -> Tumnus` rename. |
| Invalid IDs or merges | Still validated, including duplicate IDs and merge eligibility. |
| Optional identity context | Still requires matching a source phrase when supplied. |
| ScaleDown returned another character's name | A nonnull name outside approved names/aliases rejects the entire attribute update, not just its name. Raw output is retained. |
| Ambiguous same-name character | Skip attribute extraction when the current chapter provides no distinguishing name/context. |
| New aliases suggested by ScaleDown | Retain raw suggestions; approved roster aliases remain controlled by identity resolution. |
| Unknown relationship targets | Preserve as pending proposals rather than aborting extraction or inventing IDs. |
| Empty attribute updates | Preserve previous data. |

The wrong-name guard does not establish correctness: a null returned name can still carry data, and a correct returned name can accompany another person's attributes. Matching trait words to chapter text also cannot prove ownership or that they describe personality. Current concatenation of age/appearance descriptions can retain contradictions.

Earlier failures did not save the rejected LLM response, so their exact offending strings cannot be reconstructed. Do not claim those strings are known. Improving rejected-response diagnostics is a proposed follow-up.

## 7. Full-Book ScaleDown Experiments

Two real requests tested whether whole-book context improved extraction for one specified character. Each request contained all 17 narrative chapters in order, with no summary. Both used the same source hash and schema method, one request each, SDK retries disabled, and curated source-checked aliases supplied in advance. No application character IDs or Neo4j writes were involved.

| Target | Input / output tokens | Latency | API-reported cost for that call |
| --- | --- | --- | --- |
| White Witch | 55,314 / 241 | 10.38 s | $0.0021904344 |
| Susan | 55,233 / 190 | 14.757 s | $0.0021872268 |

These are recorded measurements, not future pricing guarantees.

### White Witch

Artifacts: [request, response, and assessment directory](../../book/diagnostics/scaledown_whole_book_white_witch_20261022T223919Z).

The response identified the White Witch, returned a source-backed face description and reported Jinn/giant ancestry. The latter is Mr. Beaver's account, rather than a formal taxonomy. The returned facial adjectives overlap appearance and personality.

Its Aslan relationship said she had caught him and turned him into stone. **This is not an established event.** In u09_p010–u09_p011, Edmund speculates that the stone lion might be Aslan. The response dropped the uncertainty and treated that belief as fact; u16_p003/u16_p005 concerns another lion's restoration.

The Edmund and Tumnus entries copied statements about betrayal and arrest rather than consistently describing the relationship between the two specified people. Returned aliases were supplied in the request, so their return does not demonstrate alias discovery.

### Susan

Artifacts: [request, response, and assessment directory](../../book/diagnostics/scaledown_whole_book_susan_20261022T224505Z).

Susan was chosen because she tied the White Witch for the largest number of wrong returned names in the chapter baseline: 3/13 extraction slots for Susan and 3/15 for the Witch. This ranking measures wrong names only, not all factual errors.

The response correctly focused on Susan and gave a supported adult black-hair description. However:

- `age_description: "next youngest"` belongs to Edmund in u01_p001.
- `"sister"` is a valid general relationship to Peter, Edmund, and Lucy, but omits birth order.
- `"Daughter of Eve"` was incorrectly used as her relationship description to the Professor, Aslan, and White Witch. It is a classification/address, not an interpersonal relationship or proof of parentage.
- `"Gentle"` is supported by her explicit royal epithet; it is not an independent behavior analysis.
- Adult appearance was not separated from earlier childhood descriptions.

Each experiment directory preserves `input.txt`, `request.json`, `response.json`, parsed content, `character_details.json`, metadata, assessment, and its runner. API authorization headers are not included in the request artifacts.

## 8. What the Results Establish

Whole-book input produced useful identity and simple appearance fields in these two cases, but did not solve relationship semantics, attribute ownership, chronology, or the difference between belief and fact.

The central observed failure is that wording can be present in the book while its owner, meaning, or certainty is wrong in the extracted profile. Valid JSON and a correct returned name do not establish factual accuracy.

Two different targets with one request each are not a stability benchmark or a general accuracy estimate. Do not claim ScaleDown universally fails, or that a stronger general LLM will necessarily solve every issue. The user has chosen the next approach; it still needs evidence-based evaluation.

## 9. Agreed Next Direction: General LLM Extraction With Summaries

**Planned, not implemented:** replace the current identity-only + ScaleDown profile split with full character extraction by a general LLM, and restore summary context.

```text
load validated chapters
    -> summarize_chapter graph with a better summary model
    -> extract_character graph with a better general LLM
         original current chapter
         + cumulative book summary through the previous chapter
         + accumulated character records
    -> save cumulative profiles and selected Neo4j properties
```

The summary graph can run first, but extraction must select only preceding context:

| Extracting | Summary context |
| --- | --- |
| u01 | Empty |
| u02 | u01.book_summary_so_far |
| u03 | u02.book_summary_so_far |
| uNN | Summary through u(NN-1) |

Do not pass the final book summary to early chapters or use the current chapter's generated summary as prior context. The original chapter remains the evidence; summaries are fallible aids for remembering identity, aliases, and earlier developments.

The intended extraction call should update full character profiles across chapters, including aliases, explicit attributes, relationship proposals, and identity merges. Python should retain responsibility for IDs, merge redirects, preservation of absent records, schema validation, and files. Preserve the explicit-personality-only rule.

A separate relationship-verification graph and eventual `RELATES_TO` edges remain future work. The earlier proposed edge fields included relationship type, event validity bounds, perspective character ID, confidence, status, evidence paragraph IDs, book ID, and run ID. That is not the current persisted edge model, and event IDs cannot be invented before event extraction exists.

The user will choose stronger summary and extraction models. No replacement model has been selected in this handoff. Current settings still describe the hybrid experiment:


Settings are required and loaded from `.env`; `.env.example` intentionally has blank values. Do not replace secrets or invent model defaults. Whether the separate attribute-model setting remains after the redesign is a migration decision, not a completed change.
