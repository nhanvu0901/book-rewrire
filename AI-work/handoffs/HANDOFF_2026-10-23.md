## 3. What the Application Does Today

The app is a Python CLI exposed as `pov`; it is not currently a FastAPI service or web application.

| Command/stage | Responsibility |
| --- | --- |
| `pov extract <source> --id <book_id>` | Read HTML/EPUB/TXT, map book structure with an LLM, cut narrative units, assign paragraph IDs, and write ordinary JSON/text files. |
| `pov show <book_id> [unit_id]` | Inspect saved units and paragraphs. |
| `pov ingest <book_id>` | Load the existing extracted chapters, generate summaries, accumulate character profiles, save JSON, and finally write selected Character properties to Neo4j. |
| `pov neo4j-status` | Check database connectivity and report server information. |

Phase A is already usable and the current investigation uses Narnia, book ID `narnia-debug`. Ingest does not accept the source HTML path or a `--book_id` option; it consumes that existing book ID.

The original source used during debugging was `/Users/nhanvu/.local/share/book-clone/books/lww.html`. Current output is under the repository's `book/` directory. Do not confuse that earlier source location with current ingest output paths.

`u01` identifies the first narrative unit/chapter. `u01_p001` identifies its first paragraph or source block, **not a sentence**. A block can contain several sentences. Paragraph sizes reflect the source HTML structure; they are not randomly sized chunks. A structure candidate count, such as 35, counts candidate headings/anchors, not the whole book's paragraphs.

LangGraph coordinates sequential nodes and chapter loops. There is no checkpointing, resume, parallel character extraction, or automatic continuation from a previous run directory. `recursion_limit` caps graph execution steps, not LLM reasoning depth. Each graph invocation currently uses `max(25, chapter_count * 4 + 10)`.

### Pipeline interfaces

`ingest_book(book_id, character_llm, writer, *, summary_llm, extracted_dir, ingest_dir, run_id=None, on_step=None)` is the current entry point. It takes a `JsonLLM` for characters and a `TextLLM` for summaries. There is no active `attribute_llm` argument.

```text
CLI: settings -> connect/check Neo4j -> ingest_book

ingest_book:
  validate/load chapters
  create fresh run directory
  build + invoke summarize_chapter graph
  build + invoke extract_character graph using those summaries
  write selected Character properties to Neo4j
  return IngestResult
```

The CLI checks connectivity before model calls and keeps the driver open until ingestion returns or fails. Opening/checking the connection is not a Character write.

### Summary graph

```text
START -> initialize -> summarize_chapter -> validate_summary -> save_summary
                           ^                                      |
                           +------------ next chapter ------------+
                                                        last -> END
```

For each chapter, `logic.summarize_chapter` formats the original chapter, title, chapter ID, and previous cumulative summary. The first chapter uses one plain-text call and reuses that result as the initial book summary. Later chapters use two plain-text calls on the same source input: one chapter summary and one updated cumulative summary. The second call does not consume the first call's generated summary.

Python assigns `chapter_id`, validates nonblank summary fields, and saves the result atomically. For N chapters, summary generation uses `2N - 1` logical calls before failures/retries; 17 chapters require 33.

### Character graph

```text
START -> initialize -> extract_characters -> validate_characters -> save_json
                           ^                                      |
                           +------------ next chapter ------------+
                                                        last -> END
```

Initialization checks that summaries match the chapter IDs in order. Each chapter receives the full original chapter text, the accumulated character JSON, and only the prior cumulative summary:

| Extracting | Prior summary supplied |
| --- | --- |
| u01 | Empty string |
| u02 | u01.book_summary_so_far |
| u03 | u02.book_summary_so_far |
| uNN | Summary through the preceding chapter |

The summary graph runs ahead of extraction, but current/future summary text is not passed to an earlier character call. Tests cover that boundary.

`logic.extract_characters` makes one general-LLM JSON call per chapter, with bounded semantic/schema repair attempts. `logic.validate_characters` applies identity/profile proposals on copies. The graph applies the validated result and saves it only after the chapter succeeds.

`identity.py` is still active for Python-side ID assignment and merging. Its `IdentityResponse` conversion is an internal data transformation; it is **not** another LLM identity call. `attributes.py` and the ScaleDown `AttributeResponse` schemas remain for historical experiments and tests; they are not active ingestion nodes.

### LLM adapters

All current model calls use the synchronous `OpenAI` client and `chat.completions.create`.

| Interface | Current use |
| --- | --- |
| `JsonLLM.complete_json` | Full character extraction and book structure mapping. Sends JSON-object response format, temperature 0, and configured max tokens. |
| `TextLLM.complete_text` | Summaries. Sends system/user messages and max tokens; no JSON response format or explicit temperature. |
| `EntityLLM.complete_entities` | Retained ScaleDown experiments. Uses provider-specific entity descriptions and parses `structured_result`. |

`MAX_RETRIES = 2` allows two additional schema/semantic repair attempts after the initial JSON answer. A truncated `_ask` response raises `LLMError` before that repair loop can process it. Do not describe the current code as automatically retrying truncation. SDK transport retries are a separate concern from these application repair attempts.

## 7. Character Identity, Profile, and Relationship Rules

### Record shape

Illustrative format, not a claim about the IDs of every saved run:

```json
{
  "character_id": "char_004",
  "candidate_name": "Lucy",
  "aliases": ["Lu"],
  "attributes": {
    "gender": "female",
    "species": "human",
    "age_description": "the youngest",
    "physical_description": null,
    "personality_traits": []
  },
  "relationships": {
    "char_001": "younger sister of Peter"
  },
  "resolution_status": "candidate"
}
```

Proposals also use `merged_character_ids`, usually `[]`. This is an update instruction and is not persisted as a normal character property. The legacy internal `identity_context` field is excluded from ordinary serialized records. No `mentions` list or `first_mention_id` is currently saved.

### Identity and preservation

- New proposals use unique chapter-local `new_N` IDs. Python assigns permanent `char_NNN` IDs.
- Existing identities retain their IDs when better names or aliases appear.
- Explicit merges must retain the earliest existing record and retire other known IDs. Duplicate, unknown, reused, or invalid merge IDs are rejected.
- Redirects flatten across successive merges. Retired identity relationship targets point to the surviving ID; resulting self-relations are removed.
- Names and aliases are preserved when renaming/merging; equal names alone do not cause a merge.
- The prompt requests the full updated roster, but Python also preserves omitted/absent records and empty updates.
- Known values survive null updates. Nonempty age/appearance descriptions and relationship descriptions are combined. This prevents loss but can also preserve contradictory or outdated claims.
- Gender and species accept nonempty proposed updates. Schema checks do not verify factual ownership.
- Candidate status cannot be promoted to verified by the LLM. A valid response or completed run does not certify facts.

Two brittle earlier gates were intentionally removed: requiring names to occur verbatim in the chapter, and requiring a new canonical name to belong to an existing/returned name list. They blocked valid identity references and renames. Do not restore them as a quick accuracy fix.

### Personality

The user explicitly wants **only personality descriptions written in the source**, not inferred traits based on actions. The prompt states that feelings, injuries, appearance, accusations, and teasing are not personality facts.

Python preserves old traits and accepts new wording only when that wording occurs in the current original chapter, with normalized word boundaries. This check does not prove the phrase belongs to the character, is a stable trait, or is asserted as fact. For example, Peter feeling brave in a particular moment can still pass a textual check and become an overgeneralized trait. No semantic verifier currently prevents that.

### Relationship proposals

Maps use target character IDs, not names. The description is from the source character's perspective: Peter -> Susan should describe Peter as her older brother, not Susan as his younger sister.

Known IDs, valid redirects, and temporary IDs explicitly returned in the same response can resolve. An unknown target is preserved as:

```json
{
  "source_id": "char_014",
  "target_id": "new_2",
  "description": "drawn by Father Christmas",
  "chapter_id": "u10"
}
```

Unknown temporary IDs are chapter-local. They must not be matched to unrelated `new_2` values from a later chapter. Pending proposals are not automatically verified or converted into edges. This current ID-based pending format differs from the previous hybrid's `target_name` format.

### Neo4j currently stores

The unique character key is `(book_id, run_id, character_id)`. Selected properties are `canonical_name`, `aliases`, `gender`, `species`, `age_description`, `physical_description`, `personality` as joined traits, and `resolution_status`.

The writer does not persist relationship maps or `RELATES_TO` edges, and removes legacy `first_mention_id` and `relationships` properties on matched nodes. It writes only after all character chapters complete. Current ingestion does not query Neo4j to resolve identities; the accumulated roster lives in graph state.

## 11. Neo4j Similarity Idea: Discussed, Not Implemented

The user's idea was to save each newly identified character immediately, then query Neo4j for similar existing characters when another candidate appears.

The discussion established that this is possible as an architecture, with an important distinction: similarity retrieves possible matches; it does not prove identity. `the Faun` and `Tumnus` can be the same individual despite different names; two people named Alex or two similar wolves can be different individuals.

The proposed conceptual flow was:

1. Find a candidate in the original chapter.
2. Look for exact/normalized name and alias matches within the intended book/run scope.
3. Retrieve similar profiles when necessary.
4. Let contextual evidence and identity reasoning decide whether to reuse, create, or keep an uncertain candidate separate.
5. Preserve aliases and support later explicit merging.

An alternative discussed was keeping the small active roster in graph memory while saving progress to Neo4j per chapter. For Narnia's few dozen characters, database similarity is not automatically needed to access the entire roster.

**No approach has been selected for implementation.** There is no Neo4j vector/full-text identity index, embedding generation, database candidate retrieval, per-character write, per-chapter write, or resume implementation in the current pipeline. Current writes still happen at the end.

Identity similarity would not by itself fix Aslan receiving Father Christmas's appearance or reversed relationship descriptions. Those are evidence-attribution/meaning problems, even when an identity is already known.
